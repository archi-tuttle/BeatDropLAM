## Plan: Port BeatDrop to Current MSVC

Port the active standalone Win32 executable to the MSVC/Windows 11 SDK installed with Visual Studio 2026, buildable from VS Code tasks and terminal. Keep Direct3D 9 and x86 behavior while eliminating the June 2010 DirectX SDK and third-party packages. Replace D3DX math with DirectXMath, image decoding with Windows Imaging Component, and text rendering with Windows text APIs plus a D3D9-compatible bitmap/texture path. D3DCompile supports D3D9 shader-model 2 profiles; prototype shader reflection and constant-register compatibility before broad edits.

**Findings**
- `BeatDrop.sln` references only `vis_milk2/plugin.vcxproj`, configurations Debug|Win32 and Release|Win32. The active project declares `v141`, SDK `10.0.14393.0`, ToolsVersion 14.0, imports UpgradeFromVC71 props, and uses x86 linker target. There are no x64 configurations.
- `plugin.vcxproj` includes `$(DXSDK_DIR)Include`, `$(DXSDK_DIR)\Lib\x86`, links `d3d9.lib;d3dx9.lib`, and Debug additionally hard-codes `C:\Program Files (x86)\Microsoft DirectX SDK (June 2010)\Include`. Replace the toolset and target SDK with versions actually installed under the Visual Studio installation and remove both DXSDK_DIR and absolute June SDK paths when no D3DX use remains.
- The current Windows SDK supplies D3D9 core (`d3d9.h`, `d3d9.lib`), DirectXMath, D3DCompiler (`d3dcompiler.h`/`d3dcompiler.lib`), DirectWrite, and Windows Imaging Component. Microsoft documents `D3DCompile` targets for legacy D3D9 shader-model 2, including `ps_2_a` and `ps_2_b`; the compiled code must be verified by creating D3D9 shaders. Shader reflection/constant-register mapping is not presumed to be a drop-in replacement for D3DX constant tables and needs an early prototype.
- D3DX surface: math and vectors (`D3DXVECTOR3/4`, `D3DXMATRIX`, matrix helpers) in `support.h/.cpp`, `state.h/.cpp`, `milkdropfs.cpp`, `pluginshell.cpp`, and `textmgr.cpp`; texture loading and `D3DXIMAGE_INFO` in `texmgr.cpp` and `plugin.cpp`; render-target texture helpers in `plugin.cpp` and `pluginshell.cpp`; `ID3DXFONT`/`D3DXCreateFontW` in `pluginshell.cpp`, `plugin.cpp`, and `milkdropfs.cpp`; shader compilation and reflection (`D3DXCompileShader`, `LPD3DXCONSTANTTABLE`, `D3DXHANDLE`, `D3DXCONSTANT_DESC`) in `plugin.cpp`, with consumers in `milkdropfs.cpp` and declarations in `plugin.h`.
- README.md says the DirectX End-User Runtime is needed for `d3dx9_43.dll` and `d3dx9_31.dll`. `utility.cpp::MissingDirectX` also names `d3dx9_31.dll`. Remove or revise these messages/docs after confirming the executable no longer imports D3DX at runtime; check `d3dcompiler_47.dll` deployment and existing minimum Windows support.
- Current `plugin.vcxproj` is `ConfigurationType=Application`, `TargetExt=.exe`, unlike the legacy `plugin.vcproj`, which describes a Winamp DLL (`vis_milk2.dll`, `vms_desktop.lib`, `vms_desktop.dll`). The solution selects the `.vcxproj`, so the old project is not the active build definition.
- `plugin.vcxproj` adds `..\..\musikcube\src` as an include path, but no active musikcube header include was found in the source scan (the core SDK includes in `Milkdrop2PcmVisualizer.cpp` are commented). Both post-build events nevertheless `xcopy` the built EXE and recursively copy `resources\Milkdrop2` into a sibling `..\musikcube\bin\{debug,release}\plugins\...` tree. That sibling tree is absent from this workspace; deployment should be opt-in/configurable or require an explicit checkout/path.
- No `.vscode/tasks.json` or other task definition exists. `Milkdrop2PcmVisualizer.cpp` and the audio sources use Windows SDK audio/COM APIs (`CoInitialize`, `CoCreateInstance`, `mmio*`); `winmm.lib` is pragmatically linked in `pluginshell.cpp`, `Shlwapi.lib` and D3D libs are in project settings. `ole32.lib` is not listed in the shown project dependency list, so check effective inherited linker defaults and add it if unresolved. MMCSS `AvSetMmThreadCharacteristics` use is commented out, so `avrt.lib` is not currently required by that code.
- `ns-eel-int.h` mentions `../wdltypes.h` only in its non-Windows branch; this does not block the Win32 build.

**Implementation plan**
1. **Inspect installed toolchain.** Discover the Visual Studio installation path, available MSBuild, MSVC toolset, and Windows SDK version. Confirm the C++ desktop workload and x86 compiler/linker are installed; record the exact versions instead of guessing. *No code edits yet.*
2. **Update project/build wiring.** Set `PlatformToolset` and `WindowsTargetPlatformVersion` to discovered installations; retain Debug/Release Win32 and the standalone `.exe`. Remove obsolete `UpgradeFromVC71` props only if MSBuild confirms they are incompatible/unneeded. Remove DXSDK paths and `d3dx9.lib` after D3DX callsites are ported. Audit explicit Windows libs from link errors. Make musikcube deployment optional/configurable and stage required Milkdrop resources next to the standalone output. Add VS Code tasks for Debug and Release, invoking the discovered MSBuild and `$msCompile` problem matcher.
3. **Prototype D3D9 shader replacement first.** Replace `D3DXCompileShader` with Windows SDK `D3DCompile` using the existing `ps_2_a`/`ps_2_b` profiles and diagnostics. Confirm returned bytecode is accepted by `IDirect3DDevice9::CreatePixelShader`/`CreateVertexShader`. Adapt constant/sampler reflection and register assignment to preserve D3DX constant-table behavior; verify `D3DReflect` against this legacy bytecode. If reflection is insufficient, use a small focused parser for the compiled shader's constant table metadata or equivalent explicit binding metadata. This is the first functional gate before large-scale edits.
4. **Replace D3DX math.** Use DirectXMath (`XMFLOAT3/4` for persistent fields and `XMMATRIX` at calculations where practical). Preserve matrix layout/multiplication order and D3D9 `SetTransform` behavior; compare representative preset transforms.
5. **Replace image helpers.** Decode preset textures using Windows Imaging Component (WIC), preserve supported formats, dimensions, alpha, color conversion, and mip behavior, then upload through native D3D9 texture APIs. Use `IDirect3DDevice9::CreateTexture` for render targets instead of D3DX wrappers.
6. **Replace font/text helpers.** Use DirectWrite for layout/measurement and render glyphs through a WIC-backed bitmap/custom text renderer uploaded as a D3D9 texture (or another Windows-only D3D9-compatible path). Preserve alignment, measurement, antialiasing, and Milkdrop preset text behavior.
7. **Remove legacy runtime/deployment assumptions.** Remove stale D3DX DLL checks and README requirements after verifying imports. Confirm `d3dcompiler_47.dll` deployment on the agreed minimum Windows version. Keep musikcube copies opt-in and avoid requiring a sibling checkout for standalone build/run.
8. **Run verification and fix only migration regressions.** Build Debug and Release Win32 using VS Code tasks and terminal; inspect imports; test shader compile/load and fallback, textures, fonts, resize/device reset, audio loopback, and launching from the standalone output.

**Verification**
1. Discover toolchain from VS Code PowerShell: use `vswhere` to locate the Visual Studio installation/MSBuild, check `where.exe cl` in a Developer PowerShell, and enumerate SDK versions under `$env:ProgramFiles(x86)\Windows Kits\10\Include`.
2. Build `BeatDrop.sln` in Debug and Release, Platform Win32, using the discovered MSBuild/toolset/SDK. Repeat through VS Code tasks; confirm diagnostics route to Problems via `$msCompile`.
3. For the shader prototype, compile representative shipped Milkdrop presets targeting `ps_2_a` and fallback `ps_2_b`, verify D3D9 shader creation, and compare constant/sampler register mappings and error output with the current implementation.
4. After the port, inspect the executable with `dumpbin /DEPENDENTS`; ensure no D3DX DLL/library dependency remains, and verify `d3dcompiler_47.dll` on the selected runtime baseline.
5. Run on Windows 11: device creation, preset shader compile/load/fallback, texture loading, text layout/rendering, resize/device reset, audio loopback, and launch with no musikcube checkout. Confirm resources resolve from the standalone output.

**Decisions**
- Target is the active solution's standalone Win32 `.exe`, not the legacy Winamp `.dll` project.
- Keep the Direct3D 9 renderer and x86 configuration; do not broaden to D3D11 or x64 in this port.
- Remove June 2010 DirectX SDK/D3DX dependencies and do not add third-party libraries. Use Windows SDK/Windows APIs: DirectXMath, D3DCompiler, WIC, DirectWrite, and native D3D9.
- Make musikcube deployment optional; standalone build/run must not depend on a sibling checkout.
- Default to preserving the README's existing minimum Windows support unless a replacement API/runtime proves incompatible; explicitly validate the D3DCompiler runtime availability or deployment strategy.
